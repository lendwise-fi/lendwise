# Architecture-level security and risk assessment

This is an independent design/code review, **not a completed smart-contract audit**, production penetration test, issuer reserve attestation or compliance opinion. No private optimizer implementation, signing backend or issuer service was audited. Severity is qualitative potential impact, not a CVSS score or verified exploit classification. All proposed controls require implementation and verification.

## Assets, actors and boundaries

Protect user funds/signing intent, owner sessions, issuer credentials, financial observations/history, valuation/strategy correctness and truthful product claims. Adversaries include malicious API callers, compromised issuer feeds/adapters, impersonated asset issuers, phishing sites, compromised merchant callbacks/SDK releases and otherwise honest users retrying interrupted transactions. Issuer actions such as freezing or clawback can be authorized behavior and still create investor risk.

The deployment trust-boundary diagram is in [architecture](TECHNICAL_ARCHITECTURE.md). The analytics process never gains user custody. Public market reads are separate from private investor account servicing and signed execution. Existing SEP-10 ownership must not be substituted for investor eligibility. New order routes are excluded from the core until approved.

## Stellar-specific implementation controls

Classic trustlines and contract-token balances are distinct read paths. SAC `balance(G...)` accesses the same Classic trustline balance; `balance(C...)` uses contract storage. SAC representation does not remove issuer authorization/clawback rights. Verify trustline `is_authorized`, maintain-liabilities authorization, clawback status, limits and liabilities separately; issuer flags alone cannot prove a specific holder's permission. Do not assume every Soroban token is a SAC.

Construct transactions using current account sequence, correct network passphrase, explicit timebounds/ledger bounds and exact intended source/destination/asset/amount. Validate issuer-provided XDR like untrusted input: permitted operation types, memo/destination, source changes, fee cap, contract/function/args/auth tree and expiry. No `setOptions` authority changes or unrelated operations hidden in a funding transaction. Separate Classic activation/trustline operations from resource-heavy Soroban invocation unless a documented atomic flow is deliberately supported.

Simulate Soroban with correct signer/account and ledger state; assemble resource data, inspect required authorizations, handle rent/restoration and re-simulate after restoration. Wallet consent must cover the actual executable payload. Freeze/wrong authorization/resource failures must be distinct recoverable user states, not generic “deposit complete.” Do not silently increase spending/fee limits or retry a changed intent after signing.

Existing SEP-10 controls are worth preserving: expected host/domain and network, challenge timeout/server signature, expected ManageData structure, client threshold checks, atomic consumption, session expiry/revocation and same-origin route checks. Their code presence is not a complete SEP-10 interoperability certification; contract-account/multisig/custom signer support requires explicit tests before expansion.

## Operational acceptance and incident response

RWA release requires feed-integrity alerts and pause controls with named operator/on-call owner, backup/restore rehearsal, versioned data correction procedure, secrets rotation plan and a public stale-data indicator. Trigger issuer pause on unapproved identity/code/authorization change; degrade observations with reason while keeping unaffected lending available. An incident never rewrites raw historical evidence to make a graph appear consistent.

Provider/order incidents preserve idempotency keys and audit events, stop fresh actions, reconcile chain/provider truth, then resume or escalate. Do not promise reversibility of a confirmed EVM burn, Stellar transfer or issuer token redemption. Security verification evidence belongs in tranche submissions; run a dedicated implementation audit if new contracts or material signing/execution logic are later introduced.
